# Loblaw Bio — Miraclib Immune Cell Analysis

Analysis pipeline and interactive dashboard for exploring how immune cell
populations (B cells, CD8 T cells, CD4 T cells, NK cells, monocytes) relate
to treatment response in Bob Loblaw's clinical trial data.

## Quick start (GitHub Codespaces)

```bash
make setup       # installs dependencies from requirements.txt
make pipeline    # builds the database and runs all analyses (Parts 1-4)
make dashboard   # launches the interactive Streamlit dashboard
```

`make dashboard` starts a local server on port 8501. In Codespaces, use the
"Ports" tab to open the forwarded 8501 port in your browser.

## Requirements

Python 3.9+ and the packages in `requirements.txt` (pandas, scipy,
statsmodels, plotly, kaleido, streamlit). `make setup` installs these
automatically.

## Database schema

The raw CSV is normalized into four SQLite tables rather than loaded as one
flat table:

```
projects        (project_id PK, project_name)
subjects        (subject_id PK, project_id FK, subject_name, condition,
                 age, sex, treatment, response)
samples         (sample_id PK, subject_id FK, sample_name, sample_type,
                 time_from_treatment_start)
cell_counts     (id PK, sample_id FK, population, count)   -- long/tidy format
```

Foreign keys chain `cell_counts -> samples -> subjects -> projects`, and
indexes exist on every foreign key column plus `cell_counts.population`.

### Why this design

**Normalization eliminates redundancy and update anomalies.** The flat CSV
repeats a subject's condition, age, sex, treatment, and response on every
sample row for that subject. Storing these once in `subjects` means a
correction (e.g., a mis-recorded age) only has to be made in one place, and
it's impossible for two rows about the same subject to silently disagree.

**Cell counts are stored long/tidy (one row per sample x population),
not wide (one column per population).** This is the single most important
design decision in the schema, and it's what makes the schema scale:

- *Adding a new immune population* (e.g., Treg, dendritic cells) requires
  zero schema changes — just insert more rows into `cell_counts`. A wide
  schema would require an `ALTER TABLE` and a code change everywhere counts
  are referenced.
- *Aggregate queries* (relative frequency, population totals, filtering to
  "just monocyte counts across all melanoma samples") become simple
  `GROUP BY` / `WHERE population = ...` queries instead of column-by-column
  arithmetic repeated five times.
- *Sparse or panel-specific data* is handled naturally: if a future project
  only measures 3 of the 5 populations, or adds a project-specific panel,
  the schema doesn't need per-project column sets.

**Separating `samples` from `subjects`** reflects the real-world
cardinality: one subject contributes multiple samples over time
(baseline, day 7, day 14, etc.), each with its own `sample_type` and
`time_from_treatment_start`. Mixing these into one table would force
sample-level fields (like `time_from_treatment_start`) to live awkwardly
next to subject-level fields (like `response`), and would break the
one-response-per-subject invariant.

### Scaling to hundreds of projects, thousands of samples, new analytics

This schema was chosen specifically because it degrades gracefully at
scale, rather than needing a redesign:

- **Volume**: even at thousands of samples x dozens of populations,
  `cell_counts` stays a simple, indexed, append-only table. SQLite handles
  millions of rows comfortably; if concurrent writes across many
  researchers ever become a bottleneck, the same schema ports directly to
  Postgres/MySQL with no structural changes.
- **New projects**: just new rows in `projects` — no schema change, and
  the `UNIQUE (project_id, subject_name)` constraint on `subjects` prevents
  subject-ID collisions across projects that happen to reuse naming
  conventions.
- **New analytics**: because data is normalized and long-format, new
  questions (survival analysis joining in a future `outcomes` table,
  longitudinal trajectories per subject, panel-specific population
  subsets) can be answered by adding new tables that foreign-key into
  `subjects`/`samples`, without touching existing tables or breaking
  existing queries. A wide, denormalized single-table design would require
  reshaping on every new analysis instead.
- **Metadata growth**: if subjects gain more attributes over time (e.g.,
  genomic markers, prior treatment lines), those become new nullable
  columns on `subjects` or a separate `subject_attributes` table (if
  attributes are sparse/type-varying) — again without disrupting
  `cell_counts`.

## Code structure and design rationale

- **`load_data.py`** is the single ingestion point from CSV to database.
  Every other script reads from `cell_counts.db`, never from the raw CSV
  again. This keeps one source of truth: a correction made during loading
  (or directly in the DB) is automatically reflected in every downstream
  analysis, instead of scripts drifting out of sync with stale CSV copies.
- **`analysis.py`, `stats_analysis.py`, `subset_analysis.py`** each answer
  one part of Bob's brief (Parts 2, 3, 4 respectively) and are intentionally
  kept separate rather than merged into one monolithic script. Each is
  independently runnable, testable, and readable, and each writes its own
  output artifact (CSV and/or PNG) so results are inspectable without
  re-running the whole pipeline.
- **SQL does the heavy lifting for filtering and joining** (population
  counts, cohort filters, project/response/sex breakdowns), while pandas
  handles the numeric transforms (percentages, statistical tests) that are
  awkward to express in SQL. This keeps each layer doing what it's best at.
- **`dashboard.py`** is a thin presentation layer on top of the same
  queries used in `analysis.py`/`stats_analysis.py`/`subset_analysis.py`,
  re-implemented with interactive filters (condition, treatment, sample
  type) so Bob can explore cohorts beyond the exact melanoma/miraclib/PBMC
  slice specified in the brief, without needing to edit any code. It reads
  live from `cell_counts.db` on each load (cached for performance), so it
  always reflects the current database state.
- **Statistical approach in `stats_analysis.py`**: Mann-Whitney U is used
  as the primary test (relative-frequency percentages are bounded and often
  skewed, so a rank-based non-parametric test is more defensible than
  assuming normality), with Welch's t-test reported alongside for
  comparison. Benjamini-Hochberg FDR correction is applied across the five
  simultaneous population tests — testing five hypotheses at once without
  correction inflates the false-positive rate, and reporting an uncorrected
  p-value as "significant" here would be statistically misleading.
